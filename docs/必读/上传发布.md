# #GIT — dd 本体上传发布

## 做什么

把 dd 本体的变更上传到远端仓库，**三件套硬性要求**：① push 到负责分支 ② 打日期版 tag ③ 发 GitHub Release 带更新日志。少任何一件不算发布完成。

**"发布完成"= 三件套**。默认分支同步（第 8 步）**不属于发布完成的必要条件**——默认分支未必归你管，别默认去动它；取用方拿旧版的问题用 README 写明 `clone -b <负责分支>` 解决。

**先审后发（不可违背）**：任何远端写操作（push / tag / Release）之前，必须向用户出示待推清单并获得**明确允许**。未经允许上传 = 违规，本次任务不作数。

**可复现验收（不可违背）**：发布出去的东西是**给别人在别的机器上用的**，不是给本机自己用的。任何远端写操作之前，本批改动必须有**黑盒验收证据**——按 #TEST 派无上下文 subagent 实跑，三段齐全、测试真执行。凡改动触及"别人装完能不能用"（安装步骤、分发内容、生成物、客户端接入、目录布局、依赖），验收**必须覆盖复现路径**：照仓库里的文档从头走一遍，确认文档自身足以产出可用结果。

**本机可用不算证据**（教训，2026-08-06 实例）：命令族是本机产物、不随仓库分发，而安装文档漏了生成这一步。本机一切正常、测试全绿、缓存里文件齐全——别人照文档装完却一条命令都没有。凡"生成物 / 缓存 / 链接 / 客户端注册 / 本地构建的二进制"这类不入库的东西参与交付，本机成功与他机成功**没有因果关系**。判据细则见 #CODE 的 Claim→Evidence 表。

**只进不退**：已发布的历史（分支 / commit / tag / Release）不删除不回滚——错了就用下一个版本往前修正；错误记录保留为经验，现在没用不代表以后没用。只约束**已发布的远端历史**；本地未推的 commit 在闸门被否后可自由 amend / reset。Release 正文例外：`gh release edit --notes` **补正**已发布说明是允许的（只进不退禁的是删除与回滚，不是禁止把话说得更准——发现正文里的统计数字过时、写错了链接之类，用 edit 补正）。

## 配置解析（不硬编码，按序取值）

1. 用户当次指定（如「/dd git 推到 <分支>」）
2. 本机记忆 `<INSTALL_DIR>/data/git.json`：`{"remote":"<仓库URL>","branch":"<负责分支>","layout":"<本体在仓库中的子目录，如 src/>"}`
3. 都没有 → 问一句，答案写回 git.json

`data/` 永不入库，git.json 天然只在本机，公开层 doc 里不出现任何具体仓库/用户名。

## 版本规则（日期制）

- 当日首发：`v<YYYY.M.D>-<分支>`（如 v2026.8.5-main）；「当日」按本机时区判定
- 同日再发：追加流水号 `.1` `.2` `.3`…（如 v2026.8.5.1-main）——天然单调，无时区/补零/粒度歧义。历史遗留的小时形式（如 `.00`）按只进不退保留，不再新增
- **形态区分**：`SKILL.md` 的 `version` 与 `ddBinaryVersion` 写**裸版本**（如 `2026.8.6.6`，不带 `v`、不带分支后缀）；带 `v` 和 `-<分支>` 的只有 **tag**。
- **第 4 步定版本前先查当日已发到几**：`git tag -l "v<YYYY.M.D>-*" "v<YYYY.M.D>.*"`（两个模式；别用单个 `v<YYYY.M.D>*`——每月 1/2/3 号会把 10–19 号的 tag 一并匹配进来，算出的流水号偏大），直接取下一个流水号写进两处，避免到第 7 步才发现 tag 重名、回头返工。
- 版本字符串**两处**同步：`SKILL.md` frontmatter `version`（插件 manifest 由 `gen-commands` 按它生成，不再手改）/ `scripts/dd.go` `ddBinaryVersion`（动它会触发 CI 重建二进制并回提交）

## 流程（可重跑）

前 6 步幂等，重跑无副作用（前提：版本号按上面「先查当日已发到几」一次定准）。第 7 步不幂等——tag 已存在要流水号 +1、Release 已存在改走 `edit`（见失败表），重跑产出的是**下一个**版本而不是同一个。第 8 步默认是空操作（不动默认分支）；获授权同步时幂等，已是同一提交则报 Everything up-to-date。

1. **工作区**：`<INSTALL_DIR>/data/repo` 持久克隆（无则 `git clone --filter=blob:none -b <分支>`；有则 `git fetch && git reset --hard origin/<分支>`）。不在用户目录生成任何可见工作区。
2. **回灌**：仓库有而本体没有的文件（如测试文件）先复制回本体，防漏文件。
3. **镜像**：本体 → 仓库 `<layout>`，**排除** `data/`、`commands/`、`.collab/`（工作区记忆，含本机路径，见 #MEM）、`temp/`（工作区中间物：验收沙箱 / 一次性脚本 / 备份，落工作区内是为了搬工作区时跟着走）、**顶层** `bin/`、`*.bak`、`output/`（运行产物）、`**/__pycache__/`、`scripts/*.exe`（正式二进制在 `scripts/bin/`，根下的是陈旧副本）。注意只排**顶层** `bin/`（那是安装 shim）——`scripts/bin/` 的预编译二进制由 CI 管理、随库分发，**必须保留**，误排会让别人克隆后没有可执行文件。插件清单不入库（由 `gen-commands` 生成到 `data/plugins/dd/`，克隆后跑一次即得，见 #DD）。**不带删除**——要删仓库文件必须显式操作并写进更新日志。
   **目标路径当场读 `data/git.json` 的 `layout` 拼出来，不凭记忆敲**：目标是 `<INSTALL_DIR>/data/repo/<layout>`，**不是** `data/repo`。少写这一层会把整个仓库工作区当成 EXTRA 推平（2026-08-07 实测：45 个 tracked 文件被删，靠 `git checkout -- .` 才还原）。
   **同步命令是破坏性的，先干跑**：`robocopy` 的 `/MIR`（= `/E /PURGE`）、`rsync --delete` 都是先删后报——等你从输出里看到 `*EXTRA File` 时删除已经发生了，那是回执不是预警。先加 `/L`（rsync 用 `-n`）跑一遍，确认 EXTRA 列表为空或都在预期内，再去掉干跑标志真跑。
   **排除清单不是穷举，干跑列表非空就逐个判，别照单真跑**：工作树里会长出别的会话留下的东西——2026-08-21 实测本体比仓库多 143 个文件，只有 8 个该发，其余是运行产物、字节码、陈旧二进制，以及 9 个测试残留（内容里带本机绝对路径和用户名，属第 4 步公开层纪律明令拦截的）。判不准就别镜像整棵树，**改成按本批改动清单定向拷贝**——文件数是个位数时这样最省事，也不会误伤。
   **拷贝时保持目标文件原有换行符**：读进来改一行再写回去，很容易顺手把整篇 CRLF 写成 LF，diff 会虚报成全文重写（实测一个 2897 行的 `.go` 文件，真实改动只有 1 行）。
4. **提交**：先按「版本规则」把版本字符串**两处**改掉（`SKILL.md` frontmatter `version` + `scripts/dd.go` `ddBinaryVersion`），再 `dd gen-commands` 让插件 manifest 跟上（`dd doctor` 会核这几处一致性）。然后约定式 commit（feat/fix/docs/chore + 中文摘要）。提交前 `git grep` 排查本机绝对路径/用户名，命中改占位符再提交（公开层纪律）。**别只查 `C:\Users\<用户名>` 一种形态**：2026-08-21 实测漏网的是 `C:\01_项目名` 这类盘符根下目录（目录名本身就带用户名），要按 `[A-Za-z]:\\\\` 全形态 + 用户名裸串各查一遍。**测试文件同样要查**——一份断言「正文里不许出现 X」的测试，X 就原样躺在它自己的源码里。漏改版本的表现是 tag 打出去了而 `SKILL.md` 还是旧值、`claude plugin update` 回 already latest。
5. **黑盒验收（闸门前置，不可跳）**：按 #TEST 派 fresh 无上下文 subagent 实跑本批改动，要三段齐全、测试真执行真贴输出。**触及"别人装完能不能用"的改动**（安装步骤 / 分发内容 / 生成物 / 客户端接入 / 目录布局 / 依赖）**必须验复现路径**：让 subagent 只读仓库里的文档，判断照它执行能否产出可用结果，并明确回答"照现在这份文档还会不会再犯同一个错"。收敛判据用 #TEST 的：测试全 PASS、理解与意图一致、实质性疑问 ≤ 1。未收敛就改产出物、**换 fresh subagent 重跑**，不许带着已知疑问上闸门。
   **验的必须是要发的那一份**：验收前先把第 3 步镜像跑到位，并自检**安装树里每个文件在仓库 `<layout>` 下都存在且内容相同**（排除清单内的不算）。比对手段：逐文件哈希或 `diff -r`。**别拿 `git status` 当这条的判据**——漏拷的文件在仓库树里压根不存在，`git status` 一片干净，而这条自检要防的恰恰是"漏"；它只能反过来用（改动条目数与本批预期是否对得上）。注意方向是单向的：仓库树单边多余的文件属第 3 步「不带删除」的遗留，不计入本项，要删得显式操作并写进更新日志。否则验的是本机开发树、发出去的是另一份——本 doc 这条就是被验收 agent 当场抓出来的：它发现改动只在安装树、仓库树里连函数都没有。这是"验到用户实际使用的那一层"在发布环节的具体形态（判据见 #CODE）。
6. **人工闸门**：向用户出示五样——① **改动清单**（`diff --stat` 与 `--numstat --ignore-all-space` 真实改动行数并列，后者防换行符幻影虚报）② commit 文案 ③ tag 名 ④ Release 文案 ⑤ **上一步的验收结论**（跑了几轮、剩几条疑问、复现路径验没验）——齐全后等用户明确允许。没拿到允许，后面两步一步都不许走。
7. **机械三件套（委派 `%git发布`）**：push / tag / Release 按 `%git发布` 工作流步骤 2–4 执行，其每步 verify、乱码防护与最终验收清单一并生效。参数映射：{{仓库}}=`<INSTALL_DIR>/data/repo`、{{分支}}=git.json `branch`、{{新tag}}=本 doc 流水号规则（**覆盖**其 semver 缺省）、{{changelog}}=**两段全覆盖**——①仓库内变更 ②配套生态变更（插件 / 联想族 / 本机管线），宁全勿缺。二进制不本地推——Go 源码变更时 CI 自动重建并回提交。
8. **默认分支：默认不动**。负责分支与默认分支不同名时，**不要擅自把默认分支快进过去**——它未必是你能动的分支（本项目实测：擅自快进后 CI 在两个分支各建一次二进制导致分叉，最后只能 force 回退，反而破了只进不退）。默认做法是**在 README 顶部写明 `git clone -b <负责分支>`**，让取用方显式指定，而不是去改别人的分支。
   **只有两种情况才同步**：① 负责分支就是默认分支（那本步骤天然完成）；② 明确拿到仓库 owner 授权。满足时才执行：
   ```
   git fetch origin <默认分支>:refs/remotes/origin/<默认分支>
   git merge-base --is-ancestor origin/<默认分支> origin/<负责分支>   # 前=祖先候选，后=后代；exit 0 才可 ff
   git push origin origin/<负责分支>:refs/heads/<默认分支>            # 非 force
   ```
   授权情况下的时机：等 CI 在负责分支上的回提交落地再推（`gh run list --branch <负责分支> --limit 1 --json databaseId,status,conclusion` 要 completed+success，且 `git log origin/<负责分支> -1` 顶上出现 `chore: rebuild ...`）。一跑完三件套就推，会让 CI 在两个分支各跑一遍、各产生一个平行重建提交而分叉。ff 被拒按失败表分诊，**任何情况都不许 `--force`**。

## 自我迭代

每次发布后若遇到新场景（新分支策略、新失败模式、新仓库布局），按 #DD「改 tag」流程把经验写回本 doc——公开层过滤后随下一次发布固化。

## 失败

| 现象 | 处置 |
|---|---|
| push 被拒（无权限） | 找仓库管理员开权限；应急走 fork+PR，tag/Release 待合并后在上游补打 |
| 凭据失败 | `gh auth status` 查登录；`gh auth setup-git` 让 gh 接管 git 凭据 |
| tag 已存在 | 同日流水号 +1 再打，**并回第 4 步把 `SKILL.md` 与 `ddBinaryVersion` 两处同步改成新号、重新提交**——只改 tag 会让版本串与 tag 对不上（就是第 4 步警告的那个症状） |
| Release 已存在 | `gh release edit <tag> --notes` 更新，不重复创建 |
| CI 没重建二进制 | 分两种：**流程外**的手动 push（没改 Go 源码/测试/workflow）→ 正常，本就不触发；**走本流程发布时** → 不正常，第 4 步必改 `dd.go`，CI 必触发必回提交，按第 8 步处置（停，别推默认分支，去查 run） |
| 镜像后 git status 出现删除 | 本流程不带删除，出现删除=误操作。两种成因：① **同步目标少写了 `<layout>` 那一层**（写成仓库根，整个工作区被当 EXTRA 推平）② 排除清单写错。都先 `git checkout -- .` 还原（tracked 文件全可救），删掉误建的扁平副本，再按第 3 步重跑。事后如实汇报推平了什么、怎么还原的、最终 diff 是否只剩预期文件 |
| 想跳过人工闸门直接推 | 停。出示五样清单等允许；先斩后奏=违规，写复盘 |
| 想跳过黑盒验收直接上闸门 | 停。没有验收结论的清单是不完整清单，用户没法判断该不该放行 |
| 验收只在本机跑就宣布"可用" | 不作数。本机产物不入库时本机成功≠他机成功；改安装/分发类必须验文档复现路径 |
| 验收剩 ≥2 条实质疑问却想发 | 改产出物、换 fresh subagent 重跑；疑问带进发布 = 把坑发给用户 |
| `%git发布` 缺失 | 全局层 `workflows/git发布.md` 随仓库分发；`dd list` 核对，缺失=安装不完整需重装 |
| 擅自动了不归自己管的默认分支 | 停手并如实汇报：推了几次、是不是 ff、有没有丢提交（`git log <默认> --not <负责>` 应为空）。回退需 force，与只进不退冲突，**必须用户明确要求**才做，做前先核实零损失 |
| 默认分支快进被拒（非 ff） | 停，**别 force**（只进不退同样适用于默认分支）。先 `git fetch` 拿到默认分支 ref，再 `git diff origin/<默认分支> origin/<负责分支>` 看内容（**必须带 `origin/` 前缀**，第 1 步的工作区解析不出裸分支名）：**两边内容一致**＝多半是 CI 在两个分支各建了一次二进制（见第 8 步时机），`git merge --no-ff origin/<默认分支>` 合进负责分支 → `git push origin <负责分支>` → 再重跑 ff，零内容变化、不改历史；**内容真有差异**＝默认分支上有独有改动，停下问用户怎么合 |
| 改不了默认分支设置（`gh repo edit` 回 404） | 那是无 admin 权限（404 是 GitHub 对非管理员隐藏设置接口，不是 token scope）。这本身就是"默认分支不归你管"的信号——按第 8 步默认不动，改用 README 写明 `clone -b <负责分支>`；真要改默认分支设置或同步它，都得仓库 owner 出面 |
