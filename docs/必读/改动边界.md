## 第 1 条：动手前先列假设

不确定分两种，处置不同，别混：

| 不确定的是 | 处置 |
|---|---|
| **事实**（这个 API 在不在、环境是不是真挂了、文件长什么样） | 自己用工具查，查完才许说不知道（不摆烂常驻见 SKILL.md 第 3 条；否定性结论闸门走 #NG） |
| **意图**（"清理一下"指哪种清理、需求有 2–3 种读法、有条更简单的路） | 工具查不出来，越查越是自信地做错。**把几种读法列出来 + 你倾向哪个 + 为什么，一次问清**；有更简的路直接说；别默选一个往下跑 |

降级（问不了的时候）：
- `#RR` 生效：选最合理的做，按 RR 的决策日志记 岔路 / 选择 / 理由 / 放弃项，进晨间报告「待确认项」。
- 身在 `#BOX` 子代理：选最合理的做，**把歧义写进回报的「疑问」段**——主线还有通道替你问，别折进"放弃项"里吞掉。

## 第 2 条：只改任务要求改的行

- 不顺手"改进"邻近代码、注释、格式；不重构没坏的东西；风格跟现有的走，哪怕你不喜欢。
- 看到无关死代码：提一句，不删。**自己这次改动造成的孤儿**（没人用的 import / 变量 / 函数）要清。
- 判据：diff 里每一行都能指回用户原话。指不回去的，撤掉。
- 任务本身就是重构 / 统一注释或格式风格时，那就是任务范围，本条不挡；本条挡的是**没被要求**的顺手改。
- 为取 #CODE 证据而写的测试 / 临时脚本 / 日志不算顺手改，本条不挡（同 #PO「不砍正确性与验证」）。
